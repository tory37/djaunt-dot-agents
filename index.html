One script deploys the same global instructions and skills to each supported tool. It skips a tool that is not installed.

02 — How it works

One source of truth, two targets

src/AGENTS.md is the shared system prompt. src/skills/ holds every slash command. sync.sh deploys both to the tools installed on the machine. It also clones the companion repos listed in tools/.

djaunt-dot-agents/ src/AGENTS.md ──(copy)────▶ ~/.agents/AGENTS.md ──(symlink)──▶ ~/.claude/CLAUDE.md src/skills/ ──(symlink)─▶ ~/.agents/skills/ ──(symlink)──▶ ~/.claude/skills/ │ └──(assembled)──▶ ~/.gemini/GEMINI.md (AGENTS.md + every skill inlined) tools/*.md ──(clone)───▶ ~/src/<repo>/ (companion repos and rule packs)

Claude Code

Skills natively. ~/.claude/skills/ is a symlink chain back to the repo. Skill edits are live at once. No re-sync needed.

Gemini CLI

No native skill system. sync.sh inlines AGENTS.md, plus each skill with its gemini.meta trigger, into one GEMINI.md. Re-run sync after an edit.

03 — Skills

Four slash commands, one shared harness

Each skill is a folder under src/skills/: a SKILL.md, a gemini.meta trigger for Gemini, and sometimes a reference.md with the detail. The harness is a shared folder, not a command.

Slash command /djt-work /djt-work [feature|bug|refactor] [@spec.md] View source

What it does

One workflow for features, bugs, and refactors. It splits the work into small phases. Each phase gets tests, a lint run, your check, and its own commit.

Use it when

You know the area and want the change built correctly, without a lesson.

How it runs

  1. Explore. Read the spec and the code. Detect the stacks. Record the repo's own lint commands.
  2. Clarify. Ask every open question in one message.
  3. Bug only: Gate A states the problem. Gate B states the root cause with a certainty level. Each gate stops for your approval.
  4. Plan. Write the phases to disk. Each design choice cites an official source. Wait for approval.
  5. Branch. Write the first failing test. Write the doer test plan.
  6. Per phase: implement, lint, test, stop for your check, commit.
  7. Open the PR.

You get

  • plan.html (or fix-plan.html for a bug)
  • doer-test-plan.html per phase
  • A branch with one commit per phase, then a PR
Slash command /djt-work-deep /djt-work-deep [feature|bug|refactor] [@spec.md] View source

What it does

The /djt-work flow plus a teaching layer. You learn the codebase, the architecture, the language, and best practice with each change.

How it differs from /djt-work

Same flow. Same gates. Same correctness bar: the repo's own lints, and an official source for each design choice. Deep adds three things: a recon step, micro-phases, and a cited brief per phase. A claim with no source is not built until you approve it.

Use it when

You are new to the repo or the language. Or you want to understand the change, not only ship it.

How it runs

  1. Recon. Decode the request from zero. Map the stack, the architecture, and the data flow.
  2. Clarify. Ask every open question in one message.
  3. Bug only: Gate A and Gate B, as in /djt-work. Each gate writes a brief on the failing subsystem.
  4. Plan micro-phases. Each one is the smallest change that teaches one concept.
  5. Branch. Write the first failing test. Write the doer test plan.
  6. Per micro-phase: load rules, find sources, write the brief, implement, lint, test, stop for your check, commit.
  7. Open the PR.

You get

  • Everything /djt-work gives
  • briefs/00-recon.html, a map of the codebase
  • One brief per micro-phase: Problem, Background, Solution, Evidence
Slash command /djt-test-plan /djt-test-plan [ticket | diff range | @spec.md | post] View source

What it does

Writes a tight manual test plan for one change. It also writes mitmweb scripts that inject faults for cases that are hard to reach. One plan serves the author and QA. There is no separate QA plan.

Use it when

You must test a change by hand, or QA needs steps. /djt-work calls it for each phase.

How it runs

  1. Read the diff, ticket, or spec.
  2. Keep only the cases this change can affect.
  3. Find the points that need fault injection.
  4. Ask for the environments and hosts. It never guesses an endpoint.
  5. Generate one mitmweb script per injected case.
  6. Publish the interactive plan, then stop.
  7. After you pass it locally, post the same plan to the ticket's Doer Test Plan field.

You get

  • doer-test-plan.html: an interactive artifact with links, copy buttons, and result tracking
  • A markdown plan on the ticket for QA
  • One TCn script block per injected case
Slash command /djt-frontend-design /djt-frontend-design [brief | @file | url] View source

What it does

A design pass before any UI gets built. It bans the common AI-generated look. It writes its design reasoning before it writes code.

Use it when

You build or redesign a page, a dashboard, or a component. /djt-work calls it for each phase that touches UI.

How it runs

  1. New design: read the brief. If it is vague, offer three directions and wait.
  2. Existing view: audit it. Flag weak patterns by file and line. Rank the repairs.
  3. Write a design plan: type scale, color tokens, grid, and motion. Check contrast by the numbers.
  4. Build the full artifact from the shared boilerplate.

You get

  • A one-line design read, or a design profile of the existing view
  • A ranked repair plan: Critical, Recommended, Optional
  • A self-contained, responsive HTML or React artifact
Shared layer djt-harness ~/.agents/skills/djt-harness/ View source

What it is

Shared rules that /djt-work and /djt-work-deep read. It is not a slash command. It has three parts:

  • stacks/*.md: one index per stack. It says how to detect the stack, find the repo's lint commands, reach the official docs, and pick rule-pack files.
  • citations.md: the evidence rules. Official docs first, then repo precedent. A rule pack never counts alone.
  • scripts/docs-mcp: a small script that queries a remote docs MCP server over HTTP. It needs curl and jq. Nothing gets registered.

How it loads

Just in time. A skill reads a stack file only at the step that names it, and only the rule-pack rows that match the current phase. The rest costs no context.

Stacks

react, js-ts, python, html-css, aws

Docs sources

react.dev, the MDN MCP server, docs.python.org, and the AWS Knowledge MCP server. None needs an account.

Dependencies

sync.sh reads each file in tools/. It clones each repo into ~/src and fast-forwards it. A command tool runs its install step. A vsix tool installs as a VS Code extension. A clone tool is only cloned, for agents to read.

04 — Get started

Three steps, any machine

1

Clone the repo

git clone https://github.com/tory37/djaunt-dot-agents.git ~/src/djaunt-dot-agents
cd ~/src/djaunt-dot-agents
2

Add machine-specific extensions (optional)

mkdir -p ~/.agents/extensions
cp ~/my-work-context.md ~/.agents/extensions/work.md
3

Run the sync script

bash scripts/sync.sh

It sets up Claude Code and Gemini CLI, if installed, and installs the dependencies. Re-run it after each git pull.
